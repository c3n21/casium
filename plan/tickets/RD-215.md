# RD-215 Add The Server-Side Chat Route

## Goal
Put a single server boundary between the browser and the model, so inference never ships to the client.

## Implementation
A Next route handler at `apps/web/app/api/chat/route.ts`. It accepts `{ messages, attachments }`, fetches the provider catalog server-side (`GET /listings`), calls `extractIntent`, and returns `{ reply, mandate, packet, listingMatches, rationale, llmMode }`. Fetching listings on the server rather than passing them up from the browser keeps the request payload small and stops a client from influencing the candidate set. Return `llmMode` from the resolved factory value so the UI badge in RD-216 renders truth rather than a default. Attachments arrive as base64 already (the browser has them for the packet anyway); enforce the size cap **here as well as in the UI**, because a UI-only cap is a suggestion. Keep the handler `runtime = "nodejs"` — the default edge runtime cannot load a native module, and a later `LLM_MODE=llama-cpp` would fail confusingly without it.

## Done when
- [ ] `POST /api/chat` returns a schema-valid extraction for a text-only conversation.
- [ ] `@casium/llm` appears in no client bundle — verify by grepping the built `.next` client chunks.
- [ ] An oversized attachment is rejected with a 413 and a message naming the limit.

## Verify
- **Tests.** Route tests over: text-only, text-plus-attachment, oversized attachment, and an empty message list.
- **Evidence to capture.** `curl` transcript plus the client-bundle grep.
